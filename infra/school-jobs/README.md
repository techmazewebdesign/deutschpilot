# Server-only school scheduler preparation

Nothing here installs/enables a timer or calls a real school. The source package does not establish active cron, delivery or release approval. It requires Node24 and a separately approved operator-owned host. Do not attach it to or inspect credentials in the existing n8n container.

`run.mjs` calls **POST** endpoints with a server-only file secret. Defaults are disabled, maintenance dry-run, reminders disabled and push disabled. When enabled it first requires explicit operator/controller confirmation and calls `/api/school/maintenance` in dry-run mode. The updated server must return `policyConfigured:true` after verifying the single server-configured settings row and active DB membership. Missing/partial policies, auth errors, protected-preview login/redirect/HTML responses, timeout or an old deployment without that signal stop the run before later calls. No guessed legal periods are supplied.

For approved maintenance execution set `SCHOOL_JOBS_EXECUTE_MAINTENANCE=true`; this requests one bounded batch, not complete whole-school deletion. Only after the dry-run gate succeeds can separately enabled reminders call `/api/school/notifications?push=false`. The updated server suppresses push claim/send/receipt work in this mode even if global push is enabled. `SCHOOL_JOBS_PUSH_APPROVED=true` separately requests `push=true`; global server `SCHOOL_PUSH_ENABLED`, credentials, device permissions and provider configuration still govern actual sends. A provider ticket is not physical-device display evidence. Missing the required route version is a blocker to enabling these jobs.

## Protected preview and secrets

The current preview has Vercel deployment protection. The job bearer secret authenticates the application endpoint; it does not bypass Vercel's access layer. Do not disable protection or copy browser cookies. If separately authorised and available for this deployment, the operator can mount a Vercel **automation bypass secret** file using `SCHOOL_VERCEL_BYPASS_SECRET_FILE`; it is sent only in the server `x-vercel-protection-bypass` header. Otherwise keep the timer disabled until an approved accessible target exists. No bypass credential has been obtained or configured by this package. Redirects are refused, preventing credential replay to a login/other origin. HTTPS origin validation rejects embedded credentials, paths and query strings.

Official reference checked 20 October2026: [Vercel protection bypass for automation](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation). This is an optional operator mechanism, not permission to bypass a safeguard or proof it is available in the account.

## Manual activation sequence

1. Confirm a deployed version contains the maintenance policy gate and notifications `push=false` support. Record approved target origin, active school owner maintenance UID, controller/operator contact, complete documented retention maps/notes and legal basis. Health uploads may remain disabled; routine retention must still work. The server's `SCHOOL_JOBS_CRON_SECRET` must match the external scheduler secret file; no client app receives it.
2. Install source at `/opt/school-module`, Node24 at `/usr/bin/node` (or explicitly adjust the unit), and a dedicated locked `school-jobs` service user. Create `/etc/school-jobs/operator.env` from the example. Protect job/bypass secrets outside Git with root/service-user readable permissions. Do not print or store tokens in systemd unit arguments or shell history. No example value is an operational credential.
3. Keep `SCHOOL_JOBS_ENABLED=false`; inspect the script/units and run the disabled command: `node infra/school-jobs/run.mjs` (reports disabled). Validate a **synthetic test target** before touching any school. For the approved target, enable the script but leave execution/reminders/push false for the first authenticated policy dry-run; preserve status evidence. Reminders themselves create in-app records and require approval to enable.
4. Only the authorised operator installs `school-jobs.service` and `.timer` into systemd, reviews their explicit paths/user/environment, and runs `systemctl daemon-reload`. Installation is separate from enabling. Following approval and successful dry-run, `systemctl enable --now school-jobs.timer` activates the15-minute UTC timer. No such commands were run by this preparation. `Persistent=false` avoids stale catch-up; systemd won't overlap the same running oneshot. Do not add another scheduler for the same tenant.
5. Observe actual start/completion and exit status via systemd/journal monitoring, without raw headers/response body logging. Configure an operator alert if no successful run occurs within an agreed interval (e.g. two expected intervals), on policy/auth/protection failures, unknown upload cleanup, backlog or provider error. These alerts are not provisioned. Each call is bounded; monitor backlog and tune approved cadence rather than assuming one run cleared everything.

The client sets45s per request and a180s unit timeout, never automatically retries ambiguous requests, and logs only aggregate mode/status. Existing server idempotency, leases, unknown-send handling, legal holds and durable upload cleanup remain authoritative. Failures leave queued work for reviewed retry; do not erase reservations or replay an entire historical schedule. Set `SCHOOL_JOBS_ENABLED=false` and stop/disable only this timer to pause operations. No cron, timer, provider, purchase or secret has been activated here.

Local tests: `node --test infra/school-jobs/run.test.mjs`; focused actual-handler tests: `tsx --test tests/school/scanner-jobs-routes.test.ts`. These verify control paths, not remote authentication, scheduling, delivery or legal approval.
